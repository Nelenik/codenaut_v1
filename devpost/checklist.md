## Revisions

- **The task block was one long column, so reading it and following it looked the same.** Raised by the learner: on a desktop the instruction and the how-to are two different things, and they were stacked so both had to be read off the same narrow wall of text. `TaskZone` is now a grid — the sentence with the hero on the left, "How to do it" on the right, the right column slightly wider (`md:grid-cols-[minmax(0,1fr)_minmax(0,1.15fr)]`) because the teaching block is always the longer of the two. Below `md` it is a single column and the how-to simply follows the sentence. Verified as geometry rather than by eye: on a desktop the two blocks sit at x=150 and x=741 on the same row (y=104 both), the grid reports two columns, and at phone width the grid is one column with the how-to stacked below the text at y=242.
- **A word about colour is the one word a small reader can least afford to read as letters.** Raised by the learner: the text was correct and the task was still hard, because "make it green" asks a 7-year-old to find the word "green" inside a sentence. Colour words in the task sentence and the how-to are now painted in the colour they name, with a small colour chip beside each one. Both together, deliberately — painting alone is useless for `white` and `yellow` on a dark background, and a chip alone does not connect the word to the value, so the child gets the word in its own colour *and* the swatch. The markers are `[[green]]`-style tokens, resolved in `src/lib/cssWords.ts` against the same list of colours the app can actually paint (`blue`, `darkblue`, `green`, `lime`, `orange`, `white`, `yellow`); an unknown token renders as plain text rather than leaking brackets to the child. They are only allowed in `text` and `teachBody` — the success line and the hints deliberately stay unmarked, because those are the two places where the child already has the answer and the brackets would only add noise. `colors/03` in English said "dark blue" while the value the child has to type is `darkblue`; it now says `darkblue`. `colors/05`'s English how-to named no colours at all while the Russian one did, so both now name all three and both languages paint them. Verified in headless Chrome: `colors/01` paints two words, each one `rgb(0, 128, 0)` for the word "green" with a matching chip beside it, and no `[[` survives to the screen on any task in either language.
- **The blank-picture warning was a block of text in the middle of the level screen.** Raised by the learner: warnings and errors should float as toasts, not be built into the page. `NoticeToast` (orange, `role="status"`, `aria-live="polite"`, closable by hand or with `Escape`) now carries it, pinned at the top rather than the bottom — the hint toast lives at the bottom, and a child who has blanked the picture still needs the hint, so the two must not take each other's place. Verified in the browser: the notice is `position: fixed` at top 96px, is not part of the page layout at all, appears alongside the hint rather than replacing it, and the two sit at top 96 and top 547 without overlapping. It still goes away by itself the moment the picture comes back. The "this level could not be loaded" screen stays a screen — that one has a retry button and is the whole point of the view.
- **The task block was one long column, so reading it and following it looked the same.** (Same two-column split, now shared with request 2 below.) A property name in a sentence is the one thing a 7-year-old has to type exactly, so it is given a pill that catches the eye, while the colour the child paints with is shown painted in that colour. Two requests raised together, both checked in the browser.
- **A chip in the basket arrived without a semicolon, so a child dragging one in learned the wrong thing.** Raised by the learner: the combination tasks already teach "end every command with a semicolon"; a basket chip that arrived without one put the child in the position of writing CSS the game itself had just told them is incomplete. Each draggable basket chip now reads `background-color: darkblue;` and the text the drag drops in is that exact string, so what the child sees is what lands in the editor. Verified in the browser: all 6 chips on `colors/03` end in `;`, and the drop payload is `background-color: darkblue;`. The ready-made-answer path is untouched (it writes the full valid command). The chips keep their existing cyan/lime split; only the terminating `;` was added, styled as punctuation the same colour as the colon.
- **A property name in a hint is easy to miss, and that is the one word the child has to type.** Raised by the learner: in the task text, the "how to do it" block, and the hint toasts, every CSS property name is now a bright pill — cyan background and dark letters, the same cyan the onboarding already uses for `color` in its one line of CSS, so the child cannot read past it either in teaching or when stuck. Colour words keep their paint-plus-chip treatment (now unified in `MarkedText`, shared by `TaskZone` and `ResultToast`); a property name like `background-color` is a pill, a colour like `green` is painted — two deliberately different treatments for two different things. The `wrongProperty` reply interpolates the wanted property at runtime from the checker; that name is wrapped in the same token at the call site, so it is a pill there too, not plain text. `colors/05`'s English how-to and `sizes/05`'s English how-to never named three of the properties — both now name them (the Russian already did), and the Russian `sizes/05` hint used Russian nouns ("ширина") where it should have shown the name to type — both languages now mark `[[width]]`, `[[height]]`, `[[border-radius]]` in the hint. Verified in the browser: the `colors/01` task zone paints one property pill, the `sizes/05` hint toast paints four (`width`, `height`, `border-radius`, `width`), the wrong-property toast paints the real property, and no `[[` reaches the child on any task in either language.
- **Two of the checks failed against their own output, not against the app.** Both were in the verification harness rather than the product, and both had the same shape: an assertion written against `innerText`/`textContent` stopped matching when the markup changed around it. The colour check counted the wrapper span as well as the word inside it, so every painted word was reported twice — once painted, once inherited white — and `check-learner-requests.js` failed all four colour assertions on markup the browser had already confirmed correct. The language check asserted the literal string `называется green`, but `innerText` breaks lines around an `inline-flex` element, so the phrase now arrives as `называется \ngreen`. Fixed the assertions (leaf spans only; collapse whitespace before comparing wording) rather than loosening the product. The luminance check for the property pills likewise failed first on the red channel of cyan (cyan has red 0), then on the green channel — both fixed to a real perceived-brightness formula. Recorded because it is the third time a check has been wrong about what it was reading, and the rule that comes out of it is the one that already earned its place in this document: browser behaviour in the check path gets measured, not remembered.
- **`success` was briefly routed through `MarkedText` too, and the language check refused it.** The success overlay is a reveal in the child's own language, not a coding lesson — the Russian line must read "Мячик зелёный", not the English word "green" in a chip. Reverted: the success line is plain text, the `RENDERED` set in the dictionary check is `['text', 'teachBody', 'hints']` (not `success`), and the success strings are back to natural language. Property names deliberately do not appear in any success sentence, so nothing is lost by leaving them plain, and the deliberate prior rule ("hints and success stay uncluttered") holds for colours in hints too where a colour word is reinforcement rather than something to type. Every write in `progress.ts` goes through `loadProgress()` and then mutates what it got back — but the three fallback paths (no storage, unparseable storage, server render) returned the module-level `DEFAULT_PROGRESS` **object**, arrays included. So `unlockLevel()` on a fresh game pushed into the one array every later "fresh" state was built from, and `defaultProgress()` then reported a level unlocked that nobody had played. Found by testing the store directly rather than through the UI, and only after the test harness itself was fixed: the fake `localStorage` was set on `window` while the module reads the bare global, so every "corrupt store" case was silently taking the catch path and the check was passing while testing nothing. The store now always builds a fresh state, and a stored value is sanitised field by field.
- **A corrupt store could introduce a language the game has no text for.** `{"lang":"de"}` was spread straight into progress, and i18next would have switched to a language with no dictionaries — an English player reading a Russian game with blank strings. `lang` is now checked against the two languages that ship; anything else falls back to English. A `tasks` value of `[1,2,3]` used to spread into `{0:1,1:2,2:3}`; malformed entries are now dropped instead of believed.
- **The rocket trail was drawn in full from the first minute, so it never grew.** The map now draws the whole route faintly — the road still ahead — with a lit, flowing trail clipped to how far the player has actually travelled: to the rocket with one world open, to the second planet once both are. Verified as geometry, not by eye: 50% of the path lit at clip x=300 with one world, 100% at x=480 with two, starting on the first planet in both cases, stopping at the rocket and never touching the locked planet. The clip width transitions, and `prefers-reduced-motion` turns that and the trail animation off.
- **A blank playfield said nothing.** The spec asks for a small message in the editor zone, and there was none: a child who wrote `display: none` or `width: 0` was editing against an empty box with no idea why. `PlayfieldPreview` now measures the task's own selector — its box and its computed `display` / `visibility` / `opacity` — each time the iframe loads, and the level screen says so. The check is measured, not guessed, and the editor is still one keystroke from empty, so the message tells the child to take back the last command. Verified for `display: none`, `width: 0` and `opacity: 0`, and that the message goes away when the picture comes back.
- **A level finished with no stars read as three lost stars.** The PRD asks for "completed with 0 stars, not as locked", and the row was lime with three empty stars — indistinguishable from a level not yet done. It now carries a lime tick instead, labelled "Finished without stars" / «Пройдено без звёзд». Verified that it is not shown as locked, that a starred level still shows its stars, and that the world total counts only earned stars.
- **The smallest text in the game was the player's own name.** The caption under the hero was 12px, below the spec's ~16px floor, and it is the one line of text a child sees on every single task screen. Raised to 16px, along with the three basket captions at 12–14px. Measured rather than eyeballed: no text below 14px on the map, level list, level, story or welcome screen, and every chip still fits inside the pile at 1440, 820 and 390px.
- **`spec.md > Important Failure Modes` named a message the code did not have.** It says a missing task file shows "This level could not be loaded"; the screen said `common.error` — "Something went wrong". The dedicated key now exists in both languages, with the failing path kept below it for whoever is debugging. Verified by blocking the task file at the network layer: the message appears, retry re-runs the load and reports the file is still missing, and it recovers once the file is reachable again.
- **A CDP command sent without a session id lands on the browser target, where most domains do not exist.** The harness lost several minutes to `"'Network.enable' wasn't found"` being swallowed and the process then hanging on an open socket. The check harness now reads Chrome's own `DevToolsActivePort` file (with `--remote-debugging-port=0`) so it always drives the browser it started, sends page-scoped commands through one helper, bounds every command and every navigation, and releases Chrome on the failure path.
- **The learner committed her own work in the middle of the slice** (`9661641`): `position: relative; z-index: 1; margin-bottom: 30px` on `#target` in the two sizes tasks, and wording shortened in both dictionaries. Not touched. Because it changes the very box the check measures, all ten tasks were re-run end to end through the real app — solution in, celebration out — plus a near miss per task, because a task that passes on everything proves nothing. All twenty-one assertions hold, so the sizes numbers are unaffected.
- **Playfields are confirmed clean of Tailwind.** `spec.md` calls a single utility class in a playfield "a bug — a child who reads `class="rounded-full"` learns nothing about CSS". A scan of all twenty playfield files finds no utility classes, no reference to Tailwind, no class used in markup without a hand-written selector in the same file's `<style>`, and the `CHILD_CSS` marker present in every one.
- **The early hands-on checkpoint was covered by the learner's feedback across slices 3–6, not by a separate session.** Rather than invent a pass, the box is ticked against what actually happened: five separate changes in `## Revisions` are marked "Raised by the learner" — the single-toast hint ladder, two success buttons instead of auto-advance, replay dropping stars only on a real attempt, the four-step onboarding, and the story being rewritten around the new premise. Each was decided after seeing the running app. Recorded here so the tick is honest about its evidence.
- **Dead CSS and an honest reduced-motion rule.** `.planet-glow` was defined in `globals.css` and referenced nowhere — the planets get their glow from Tailwind's `drop-shadow-*`, so it was removed rather than left to rot. The `prefers-reduced-motion` block originally listed a `.celebrate` class that no element carried; it now names what actually animates (`.rocket-trail`, `.animate-bounce`, the trail's clip), which works because unlayered CSS outranks the layer Tailwind emits `animate-bounce` into.
- **A store bug that no UI test would have caught.** See the `loadProgress()` revision above. It is recorded here as the lesson rather than only as a fix: the first version of the check passed while testing nothing, because the fake `localStorage` sat on `window` and the module read the bare global. A test that cannot fail is worse than no test, because it reports safety.
- **No linting in this project.** `npm run lint` runs `next lint`, which is deprecated in Next 16 and prompts to create an ESLint config; there is no config in the repo. Type checking (`npx tsc --noEmit`) is clean and stays the gate. Adding ESLint is a choice for the learner, not something to slip into a polish slice.

- **A returning Russian player was shown English for a moment before the switch.** `localStorage` cannot be read while the server renders, so the server always sends English HTML; the stored language used to be applied in an effect afterwards, which meant the header and the loading line painted in English and then changed. Rendering the stored language during SSR is not available either — the client would then render a different language from the one the server sent, a hydration mismatch. `I18nProvider` now renders nothing but the bouncing rocket until the stored language has been applied, so the first paint carries no text at all and the real screen appears already in the right language. Verified in headless Chrome by sampling the DOM on every frame after `loadEventFired`: no frame contains an English word for a player whose stored language is `ru`.
