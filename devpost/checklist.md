## Revisions

- **`loadProgress()` handed out the shared default, so the first thing that unlocked a level polluted it.** Every write in `progress.ts` goes through `loadProgress()` and then mutates what it got back — but the three fallback paths (no storage, unparseable storage, server render) returned the module-level `DEFAULT_PROGRESS` **object**, arrays included. So `unlockLevel()` on a fresh game pushed into the one array every later "fresh" state was built from, and `defaultProgress()` then reported a level unlocked that nobody had played. Found by testing the store directly rather than through the UI, and only after the test harness itself was fixed: the fake `localStorage` was set on `window` while the module reads the bare global, so every "corrupt store" case was silently taking the catch path and the check was passing while testing nothing. The store now always builds a fresh state, and a stored value is sanitised field by field.
- **A corrupt store could introduce a language the game has no text for.** `{"lang":"de"}` was spread straight into progress, and i18next would have switched to a language with no dictionaries — an English player reading a Russian game with blank strings. `lang` is now checked against the two languages that ship; anything else falls back to English. A `tasks` value of `[1,2,3]` used to spread into `{0:1,1:2,2:3}`; malformed entries are now dropped instead of believed.
- **The rocket trail was drawn in full from the first minute, so it never grew.** The map now draws the whole route faintly — the road still ahead — with a lit, flowing trail clipped to how far the player has actually travelled: to the rocket with one world open, to the second planet once both are. Verified as geometry, not by eye: 50% of the path lit at clip x=300 with one world, 100% at x=480 with two, starting on the first planet in both cases, stopping at the rocket and never touching the locked planet. The clip width transitions, and `prefers-reduced-motion` turns that and the trail animation off.
- **A blank playfield said nothing.** The spec asks for a small message in the editor zone, and there was none: a child who wrote `display: none` or `width: 0` was editing against an empty box with no idea why. `PlayfieldPreview` now measures the task's own selector — its box and its computed `display` / `visibility` / `opacity` — each time the iframe loads, and the level screen says so. The check is measured, not guessed, and the editor is still one keystroke from empty, so the message tells the child to take back the last command. Verified for `display: none`, `width: 0` and `opacity: 0`, and that the message goes away when the picture comes back.
- **A level finished with no stars read as three lost stars.** The PRD asks for "completed with 0 stars, not as locked", and the row was lime with three empty stars — indistinguishable from a level not yet done. It now carries a lime tick instead, labelled "Finished without stars" / «Пройдено без звёзд». Verified that it is not shown as locked, that a starred level still shows its stars, and that the world total counts only earned stars.
- **The smallest text in the game was the player's own name.** The caption under the hero was 12px, below the spec's ~16px floor, and it is the one line of text a child sees on every single task screen. Raised to 16px, along with the three basket captions at 12–14px. Measured rather than eyeballed: no text below 14px on the map, level list, level, story or welcome screen, and every chip still fits inside the pile at 1440, 820 and 390px.
- **`spec.md > Important Failure Modes` named a message the code did not have.** It says a missing task file shows "This level could not be loaded"; the screen said `common.error` — "Something went wrong". The dedicated key now exists in both languages, with the failing path kept below it for whoever is debugging. Verified by blocking the task file at the network layer: the message appears, retry re-runs the load and reports the file is still missing, and it recovers once the file is reachable again.
- **A CDP command sent without a session id lands on the browser target, where most domains do not exist.** The harness lost several minutes to `"'Network.enable' wasn't found"` being swallowed and the process then hanging on an open socket. The check harness now reads Chrome's own `DevToolsActivePort` file (with `--remote-debugging-port=0`) so it always drives the browser it started, sends page-scoped commands through one helper, bounds every command and every navigation, and releases Chrome on the failure path.
- **The learner committed her own work in the middle of the slice** (`9661641`): `position: relative; z-index: 1; margin-bottom: 30px` on `#target` in the two sizes tasks, and wording shortened in both dictionaries. Not touched. Because it changes the very box the check measures, all ten tasks were re-run end to end through the real app — solution in, celebration out — plus a near miss per task, because a task that passes on everything proves nothing. All twenty-one assertions hold, so the sizes numbers are unaffected.
- **Playfields are confirmed clean of Tailwind.** `spec.md` calls a single utility class in a playfield "a bug — a child who reads `class="rounded-full"` learns nothing about CSS". A scan of all twenty playfield files finds no utility classes, no reference to Tailwind, no class used in markup without a hand-written selector in the same file's `<style>`, and the `CHILD_CSS` marker present in every one.
- **The early hands-on checkpoint was covered by the learner's feedback across slices 3–6, not by a separate session.** Rather than invent a pass, the box is ticked against what actually happened: five separate changes in `## Revisions` are marked "Raised by the learner" — the single-toast hint ladder, two success buttons instead of auto-advance, replay dropping stars only on a real attempt, the four-step onboarding, and the story being rewritten around the new premise. Each was decided after seeing the running app. Recorded here so the tick is honest about its evidence.
- **Dead CSS and an honest reduced-motion rule.** `.planet-glow` was defined in `globals.css` and referenced nowhere — the planets get their glow from Tailwind's `drop-shadow-*`, so it was removed rather than left to rot. The `prefers-reduced-motion` block originally listed a `.celebrate` class that no element carried; it now names what actually animates (`.rocket-trail`, `.animate-bounce`, the trail's clip), which works because unlayered CSS outranks the layer Tailwind emits `animate-bounce` into.
- **A store bug that no UI test would have caught.** See the `loadProgress()` revision above. It is recorded here as the lesson rather than only as a fix: the first version of the check passed while testing nothing, because the fake `localStorage` sat on `window` and the module read the bare global. A test that cannot fail is worse than no test, because it reports safety.
- **No linting in this project.** `npm run lint` runs `next lint`, which is deprecated in Next 16 and prompts to create an ESLint config; there is no config in the repo. Type checking (`npx tsc --noEmit`) is clean and stays the gate. Adding ESLint is a choice for the learner, not something to slip into a polish slice.

- **A returning Russian player was shown English for a moment before the switch.** `localStorage` cannot be read while the server renders, so the server always sends English HTML; the stored language used to be applied in an effect afterwards, which meant the header and the loading line painted in English and then changed. Rendering the stored language during SSR is not available either — the client would then render a different language from the one the server sent, a hydration mismatch. `I18nProvider` now renders nothing but the bouncing rocket until the stored language has been applied, so the first paint carries no text at all and the real screen appears already in the right language. Verified in headless Chrome by sampling the DOM on every frame after `loadEventFired`: no frame contains an English word for a player whose stored language is `ru`. The gate is deliberately language-free markup, because it has to be byte-identical on the server and on the client.
- **`<html lang>` did not follow the switch.** It was written once when the provider mounted, so a player who switched to Russian still had `lang="en"` on the document — wrong for a screen reader. The provider now listens for i18next's `languageChanged` and updates it on every switch.
- **A Russian child was asked for a word the game had never shown them.** Found by the slice-7 dictionary check, not by reading: on `colors/05` the task has no basket chip to copy from, so all three commands are typed — and the Russian text said «внутри синий, рамка жёлтая, буквы белые» and never once named `blue`, `yellow` or `white`. The English text does, only because "blue" is both the English word and the CSS value. `colors/05` now names the three values in Russian, and `sizes/05` names `width`, `height` and `border-radius` for the same reason. The rule is now mechanical rather than remembered: a task with no basket chip must name every value it expects, in its own text, in both languages, and a basket task must offer the wanted property with the wanted value.
- **Three child-facing strings were still hardcoded in English.** `Loading` said "Loading…", the reference iframe's title was built as `` `${title} — reference` ``, and the toast's dismiss button was `aria-label="close"` — none of them went through the dictionaries, so a Russian player saw English on the loading line and an English screen-reader name. All three now come from the dictionaries (`common.loading`, `level.referenceFrame`, `toast.close`). A scan of every `.tsx` file for literal text in JSX and for literal `aria-label` / `title` / `placeholder` / `alt` attributes now finds nothing.
- **`LevelList` showed "Loading…" when the world did not exist.** It used `common.loading` on the error branch, so a bad `/play/colourz` URL reported a progress message instead of an error. Now `common.error`.
- **`common.loading` had drifted out of the dictionaries in a different way.** It existed in both languages and was rendered by one screen — but `Loading.tsx` had replaced it with a literal, which is how the key came to look unused. Both dictionaries were also hand-edited out of canonical formatting (a key at column 0, no trailing newline), so a duplicate-key check built on a JSON round-trip would have been a formatting check wearing a duplicate check's name. It is now a real parser that walks the document and compares against `JSON.parse`, so it reports duplicates whatever the formatting.

- **The basket is a scatter of whole commands, and nothing may cover anything.** Raised by the learner, twice: first that a chip must show the property *and* the value and the pile should look thrown together, then that the heap was wrong — chips lay on top of each other and part of the properties could not be read. Replaced absolute positioning with an ordinary wrapping flex row where each chip carries a fixed-table offset and a small tilt: the browser does the layout, so two chips cannot cover each other at any window width. Two things the measurement caught that the eye would not: a negative `marginTop` pulls a chip into the row above without the row growing to make room (so layout boxes stop overlapping and the cards do not), and a card rotated a couple of degrees is a few pixels wider and taller than the box it is laid out in, which is why the row carries padding. Verified in headless Chrome at 1440, 820 and 390px: six chips, nothing clipped, nothing covering anything. Chips keep the spot they were dealt to — their index in the task's basket — so taking one out does not shuffle the rest under the child's cursor.


- **The basket is a heap, and it hands over whole commands.** Raised by the learner: a chip must show the property *and* the value, and the pile should look thrown together rather than lined up in a row. The chips are absolutely positioned from a fixed table — a tilt, a step and an offset each — so the look is scattered but stable: a chip keeps the spot it was dealt to, taken from its index in the task's basket, so taking one out does not shuffle the rest under the child's cursor. Since browser behaviour had already been misremembered once, the geometry was measured rather than eyeballed, and the first attempt failed: the container was 160px tall while a tilted 275px-wide chip is 54px tall, so the top and bottom chips were being clipped. Chips now have a fixed height and the pile reserves room for the tilt on every side. Verified in headless Chrome at 1440px and at 375px: six chips, none clipped, none hidden under another, every one still grabbable.


- **Every playfield is `box-sizing: border-box`.** Decided by the learner: a width or height a child writes is the whole shape, with the padding and the border inside it. `getComputedStyle` reports that same outer number, so no special measuring was needed — I first assumed it returned the content box, wrote a border-box measuring path, and was wrong; the learner pushed back, and headless Chrome settled it (`border-box`: computed `160px`, rect `160`; `content-box`: computed `160px`, rect `224`). The measuring path was reverted. The general lesson is recorded because it is not a detail: browser behaviour in the check path gets measured, not remembered.
- **Rounding and every other size are now verified in a real browser.** Added at slice 6 after being wrong about what `getComputedStyle` returns: each task's assembled playfield is loaded into a headless Chrome, the real `check()` runs against the measured values, and the task is confirmed to pass — and to fail on the near misses — in the browser the game will actually run in. The same run confirmed the rounding case from the other direction: on a 120px square Chrome reports `border-radius` `60px` as `"60px"` but `50%` as `"50%"`, which is why percentages need the `round` mode.


- **A dragged property arrives with its value, and the basket is a live list.** Raised by the learner at the slice-6 learner check, three decisions in one: the chip dropped into the editor is a complete command (`background-color: darkblue`), a property that has been dragged out is no longer offered, and a property taken out of the editor comes back to the basket. What the basket offers is therefore *derived* from the editor text through `parseDeclarations` rather than kept in its own state — so it cannot drift, and the chip also returns if the child simply deletes the text instead of pressing the button. Each placed property gets a `×` to take it back out. `prd.md > Task progression within a world` and `scope.md` were corrected: the ladder is now "name given, type the value → pick the name, the value comes with it → type both".
- **"Right look, wrong property" is now a colour-only outcome.** A consequence of the above, caught before it reached her: with the value inside the chip, `sizes/03` puts `width: 160px` right next to a task that wants `height: 160px`. The old check compared the *computed number* of whatever property was written against the expected number, so that chip earned "you got the look you wanted — well done!" for a picture that was wrong. `width: 160px` and `height: 160px` are the same number and not the same image, so only a colour can now produce this outcome. A length gets the hint instead, which is the honest message.
- **`border-radius` is checked as a shape, not as a number.** Raised by the learner at the slice-6 learner check: she tried percentages and they never passed. The cause was in the check, not the browser — `getComputedStyle` returns `border-radius` exactly as written, so `50%` stays `50%` and was being compared against pixels. A corner radius also resolves against the box it rounds, which means `60px`, `50%` and `100%` are literally the same circle on a 120-pixel square. A third mode, `round`, takes no `value` at all: it resolves each of the one-to-four corners (and the `/` vertical pair) against `getBoundingClientRect()` and asks whether every corner reached the middle. Half the size, 50% and 100% all pass; `10px` and `5%` still fail, because they only round the corners part of the way.
- **Basket tasks show the right property with a different value.** Corrected by the learner after my first attempt: I had put an unrelated property in the example (`text-align: center`) to avoid hinting at the answer, which read as a mistake in a block that talks about `border-color`. The example is now the property the task needs, carrying a value that is not the one wanted — `background-color: blue`, `border-color: red`, `height: 90px`, `border-radius: 50%` — so it teaches the shape of the answer without handing it over, the same pattern the given-property tasks use. One exception, deliberate or not: on `sizes/04` the example is a value the check accepts, since `50%` really is the same circle as the dragged `60px`.
- **The task text moved from the bottom bar to the top of the level screen.** Raised by the learner: half the task sat below the fold, so it was cut off exactly where the instruction lives. It now sits under the header, above the editor and the preview, and the two columns keep their 40/60 split.
- **Task 5 is several named properties, all required — not a free choice.** Corrected by the learner: the PRD said "2–3 properties of the child's choosing", which would have made the last task of each world uncheckable. A combination task is the same rule applied three times, so all three must hold. An answer with the right value under a neighbouring property name is still the friendly `rightLookWrongProperty` outcome, naming the property the task wanted.
- **The `CHILD_CSS` marker was a promise no playfield kept.** `CHILD_CSS_MARKER` was `<!--CHILD_CSS-->`, an HTML comment, but every task file contains the CSS comment `/* CHILD_CSS */` inside its `<style>` block — so all ten tasks were silently using the `</style>` fallback in `assemblePlayfield()`. Found by the slice-6 verification script, which checks the marker the way the docstring describes. The constant is now the marker the files actually carry; the fallback stays as a safety net.
- **Hint text and the success sentence live in the dictionaries only.** `task.json` had a `hints` array of i18n keys that nothing read (the app reads `tasks.<id>.hints.0`), and `level.success` held "Great job! The ball is green." — one task's sentence in a shared key. Both fields are gone; hint text is `tasks.<id>.hints[0]` and each task owns `tasks.<id>.success`, in both languages.
- **`givesValue` is gone from `task.json`.** Nothing read it, the stage is already fully described by `givesProperty` (pre-filled editor) plus `basket` (pick it yourself), and its value on task 1 was the opposite of what happens there — the property is given, the value is typed.
- **Drag-and-drop needed the app to allow the drop.** CodeMirror 6 registers no `dragover` handler, so the browser refuses the drop before any handler runs. `CssEditor` cancels `dragover` on its wrapper, and handles `drop` in the capture phase so the editor's own drop handler cannot insert a second copy — one drop, one `property: `, inserted where the child dropped it, with a line break when it follows something else. Known limitation, chosen knowingly: HTML5 drag-and-drop does not fire on a touch screen, so the basket needs a mouse or trackpad.
- **Task 5 texts are written but the scenarios are placeholders.** Raised by the learner at the slice-6 review: the ten scenarios (ball, moon-base sign, night sky, school sign, badge, door, rocket, window, square planet, portal) exist so the world is playable end to end, and will be reworked later. The expected colours are all named CSS colours, so every answer stays reachable by a 7-year-old typing one word.

- **The onboarding's first screen is the story text itself, and the book no longer repeats it.** The story was being shown twice with slightly different surroundings, so `story.text` became onboarding screen 1 (`story.greeting` is its title) and the book is now just the replay button plus a one-line pointer. Shortened the story — it was the longest screen in the onboarding by a wide margin, which is wrong for a 7-year-old reading it once.
- **HTML and CSS are now characters: a builder and an artist.** `builder.svg` lays blocks, `artist.svg` holds a brush and palette. The metaphor replaces "makes the parts / changes how they look" because a role is something a 7-year-old already understands, and a role is what they will be doing — they are being handed the painter's job for the rest of the game.
- **Added a 4-step onboarding after the name, skippable and replayable from the book.** Raised by the learner, with the scenario worked out in detail: one idea per screen (welcome → HTML and CSS work together → a CSS command and its parts → the planets ahead), each with a visual example, and no real syntax beyond `color: blue;`. "Property" is deliberately not used as the primary word — the screen says `color` is "the name of the ability" and `blue` is "the value", which is the idea the child needs first; the real terminology arrives through the tasks. Lives at `/welcome`, gated on `onboardingDone`, so it runs once and never interrupts a returning child; the book screen has a button to replay it.
- **The whole hint ladder lives in one toast.** Raised by the learner: the guiding words were in the toast while the reveal and solution buttons sat in a separate block below, so a child had to work out that they belonged together. `HintLadder` is gone — `ResultToast` now carries the words, the blurred answer, "Show me" and "Use the ready-made answer", and the `showingHints` state went with it since the toast is already driven by the check result.
- **Hints live in the task's `hints` array only, and surface in a floating toast.** Raised by the learner: `level.hint1/hint2/hint3` were rendered from nowhere, did nothing, and duplicated the per-task hint text in two places. Removed those plus `starsAwarded`, `levelComplete`, `nextLevel`, `levelList.title/stars/locked` and `map.language`; a script confirmed EN and RU now have identical key sets and no duplicate keys. The hint ladder now holds only the two mechanisms (blurred answer, ready-made solution) — the first rung is the toast, so the same words never appear twice in two boxes. Result messages became `ResultToast`: warm amber, non-blocking, dismissible, and it stays until acted on rather than timing out.
- **Replay drops the previous stars when the child writes something and presses Check — not when they open the level.** Decided by the learner after I flagged that the PRD's original wording wiped a score just for entering a completed level. `prd.md > Level list` corrected in the same pass. "Wrote something" is measured with `parseDeclarations`, so the pre-filled `background-color: ` with no value counts as nothing typed; verified across prefilled, empty, whitespace and typed cases.
- **Success now offers two buttons instead of moving on automatically.** Raised by the learner. This overrides `prd.md > Check and result` ("no separate next click"), and the PRD was corrected in the same pass. The reason is solid: a child who finishes the *last* task of a world has no next task, so a single "next" button would be a lie at the exact moment the game most wants to reward. Two buttons — on to the next task, or back to the level list — also let the child stop and look at what they just unlocked.
- **Success unlocks the next level and moves on by itself.** `recordTaskSuccess` was being called without `unlockLevel`, so passing a task changed nothing. `nextLevel()` / `worldAfter()` in `worlds.ts` derive the next target from the level list, and completing `colors/05` lights up `sizes/01`.
- **Task targets must be authorable as a value a child can type.** The first version of task 1 expected `#00c85a`, and the verification showed a child writing `lime` would be refused — both are green. Expected colours are now named CSS colours (`green` = rgb(0,128,0)) and the teaching block names the colour, so the answer is reachable by a 7-year-old. Verified `lime` correctly fails against `green`: matching the *target* is the lesson, and the reference overlay is how the child sees which target.
- **`expect` covers one property, so combination tasks will need `expects: []`.** Recorded now, at slice 4, so slice 6 does not silently build five tasks against a shape that cannot hold them. `check()` already iterates over every declaration the child wrote and asks the browser what each one computed to, so only the config shape changes.

Editor and preview are now two columns (`lg:grid-cols-5`, 2 and 3), and the task text runs along the bottom as a speech block with the hero drawn as the narrator. - **The reference is now a cursor-following wipe, not a permanent overlay.** Raised by the learner at the slice-3 hands-on check, the CSS Battle pattern: the reference iframe is full size and clipped with `clip-path: inset(0 X% 0 0)` where X follows the pointer, so the child sees their result on the left and the target on the right, split exactly under the cursor, with a yellow divider. Position is written directly to the node via a ref — routing it through state would re-render the whole level screen on every mouse move.
